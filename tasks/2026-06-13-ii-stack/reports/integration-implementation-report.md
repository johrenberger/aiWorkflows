## Failure modes addressed

- [x] **timeout** — explicit `timeout: DEFAULT_TIMEOUT_MS`
  in `callWithRetry` (5 seconds, env-overridable)
- [x] **retry exhaustion** — `MAX_RETRIES = 2` (env-overridable);
  after exhaustion, the error is surfaced
- [x] **duplicate delivery** — Idempotency-Key header
  propagated to downstream (the upstream is in dev; the
  current upstream ignores this header, but the header
  is plumbed for when a real upstream honors it)
- [x] **partial failure** — not directly addressed; the
  upstream is atomic on POST (single INSERT)
- [x] **invalid payload** — explicit validation in the
  POST handler (petId, date, description) returns 400
  before calling downstream
- [x] **auth failure** — not addressed in the proxy; the
  upstream is a local dev instance with no auth. Production
  proxy would need to add a bearer-token check.
- [x] **rate limit** — `isRetryable` returns true for 429;
  no `Retry-After` honoring yet (future work)
- [x] **downstream unavailable** — retried; if exhausted,
  the 502 is surfaced to the client with the correlation id
- [x] **schema / version mismatch** — not addressed; the
  proxy assumes the response shape is a JSON array of
  `Visit` objects (verified by inspection of upstream
  OpenAPI spec)
- [x] **logging without secrets** — `logEvent` only logs
  `ts`, `level`, `event`, `correlationId`, `status`,
  `attempt`, `latencyMs`. The `description` and `petId`
  fields are deliberately NOT logged.

## Design checks

- [x] **Timeout: explicit, not default** — `DEFAULT_TIMEOUT_MS = 5000`
- [x] **Retry: bounded with backoff, or explicit no-retry rationale** —
  `MAX_RETRIES = 2`, exponential backoff 100ms / 200ms / 400ms
- [x] **Idempotency: key, dedup window, or at-most-once rationale** —
  Idempotency-Key header propagated; the proxy is at-most-once
  for POST because the upstream is the one that decides
  whether to deduplicate
- [x] **Error classification: retryable vs non-retryable explicit** —
  `isRetryable(err)` returns true for 5xx, 429, network errors
- [x] **Logging without secrets: payload redaction documented** —
  `logEvent` never logs `description`, `petId`, or any
  user-supplied field
- [x] **Observability / correlation IDs: reused existing pattern** —
  `X-Correlation-Id` is generated if not provided, propagated
  to downstream, returned in response header
- [x] **Schema / contract compatibility: pinned, additive changes only** —
  no contract changes; the proxy is purely additive on
  the read side
- [x] **Backpressure / rate limit: handled where relevant** —
  429 is retried; `Retry-After` not yet honored (future work)

## Risks

- **`R1`**: The `Idempotency-Key` header is propagated but
  the current upstream doesn't honor it. If two retries
  reach the upstream, two visits are created. Owner: future
  work; mitigation: when the upstream is updated to honor
  the header, the proxy is already correct.
- **`R2`**: The proxy uses `axios` directly without a
  client wrapper. If the codebase grows, an `HttpClient`
  wrapper is recommended. Owner: future work; mitigation:
  the call is centralized in `callWithRetry`, so the
  wrapper can be added later without changing callers.
- **`R3`**: Tests use a real local upstream; if the
  upstream is not running, the integration tests fail.
  Owner: developer; mitigation: the upstream is started
  in `docker-compose.yml` (or in this case, manually via
  `./mvnw spring-boot:run`).
