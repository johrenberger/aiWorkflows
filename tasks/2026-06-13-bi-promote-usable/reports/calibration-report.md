## Why `usable` (not `validated`)

The `usable` level requires "skill has been exercised and
produces valuable artifacts." That is met: 3/3 use cases
produced all 3 artifacts.

The `validated` level requires "skill has been proven to
catch issues a no-skill run would miss." That is NOT met:

| Metric | UC1 (no skill) | UC2-4 (with skill) | Δ |
|---|---|---|---|
| Time | 5:36 mean | 12:08 mean | **2.2x slower** |
| Auditable artifacts | 0 | 6 (2 per use case) | **+6** |
| Bugs caught by skill | n/a | **0** | n/a |
| Bugs introduced by skill | n/a | **1** (UC3 `@Cacheable` reverted) | n/a |

**Honest verdict:** The skill is a **discipline tool** that
produces audit artifacts and prevents specific classes of
bug (no new deps, no Lombok, no destructive migrations).
It does NOT replace code review or domain knowledge, and
can introduce issues for advanced patterns (caching, async,
transactions).

## Skill maturity assessment

### Strengths (kept by the skill)
- Forces reading the `java-spring` profile before starting
- Enforces a structured implementation report
- Produces a handoff packet for the next agent
- Runs `validation-runner` at the end

### Weaknesses (not caught by the skill)
- Does NOT catch runtime/semantic issues (JPA + cache
  footgun in UC3)
- Does NOT require running the **existing** test suite
  before considering the change done
- Does NOT check for cross-test pollution (cache + eager
  associations)
- Does NOT warn about `@AutoConfigureMockMvc` being
  unavailable in some Spring Boot versions

### Recommended follow-ups (NOT part of this promotion)
- Add JPA-aware cache guidance to `java-spring` profile
- Add explicit step "run the existing test suite" before
  the implementation step
- Consider promoting to `validated` after 4+ use cases
  with a positive catch (skill caught a real bug)
