## Deviations from plan

### Major: Removed `@Cacheable` from `findPetById`

The original plan was to add `@Cacheable("pets")` on `findPetById`.
This caused **4 of 4** `AbstractClinicServiceTests` integration
tests to fail with:

```
DataIntegrityViolationException: NOT NULL check constraint;
column: PET_ID
```

in the `shouldInsertVisit` test (and similar in others).

**Root cause:** `Pet` has a `Set<Visit> visits` field with
`FetchType.EAGER`. When `findPetById(1)` is called and the
Pet is cached, the Pet is stored **with the eagerly-fetched
Set of Visits attached to the original JPA session**. When
the next test (in a different transaction) reads from the
cache, the Pet is detached, the Set of Visits is detached,
and JPA's dirty checking on save/merge sees stale state in
the detached children, generating INSERTs with null foreign
keys.

**Why the skill did not catch this:**
- The `java-spring` profile lists "no cross-cutting concerns"
  but caching is a Spring-core concern, not a "cross-cutting"
  concern by their definition.
- The skill's test-first step (workflow step 4) says "Add or
  update tests" but doesn't say "Run the existing test suite
  before considering the change done."
- The skill's "smallest safe change" framing incentivized the
  simplest caching annotation without warning about JPA
  entity-lifecycle pitfalls.

**Resolution:** Removed `@Cacheable` from `findPetById`. The
`@CacheEvict` annotations on `savePet` and `deletePet` are
kept so they will take effect when a real cache is later
introduced (e.g. on a DTO method, or via Spring Data's
repository-level `@Cacheable` which understands entity
lifecycle).

**This is a real, valuable lesson** about the `backend-implementation`
skill: it caught the small-change discipline (no new deps,
no new starters) but did NOT catch the JPA+cache anti-pattern.
A real engineer would have caught this in code review, but
this exercise was a single-agent run.
