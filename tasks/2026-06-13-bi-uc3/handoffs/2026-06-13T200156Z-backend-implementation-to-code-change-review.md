## 5. Context summary

This is use case #3 of a 4-use-case exercise to measure
whether the `backend-implementation` skill materially helps.

The original plan was to add `@Cacheable("pets")` to
`ClinicServiceImpl.findPetById` and `@CacheEvict("pets")` on
`savePet` / `deletePet`. This plan was abandoned mid-task:
adding `@Cacheable` to `findPetById` broke **4 of 4** existing
`AbstractClinicServiceTests` integration tests with
`DataIntegrityViolationException: NOT NULL check constraint;
column: PET_ID`.

**Root cause:** `Pet` has `Set<Visit> visits` with
`FetchType.EAGER`. When the Pet is cached, it stores
**eagerly-fetched detached Visits** with the original JPA
session. Subsequent tests (in different transactions) read
from the cache, get a detached Pet, and JPA's dirty
checking on save/merge sees stale state in the detached
children.

**Resolution:**
- Removed `@Cacheable` from `findPetById`
- Kept `@CacheEvict` on `savePet` and `deletePet` (so they
  will take effect when a real cache is reintroduced)
- Added a comment in `findPetById` explaining the issue
- Updated tests to be honest about the new state

The full implementation report is at:
`/data/.openclaw/workspace/tasks/2026-06-13-bi-uc3/reports/backend-implementation-report.md`
