### 11 decisions made across the 5 phases

- **`D1`**: Use `pyyaml` and `click` (standard, no lock-in).
- **`D2`**: All analyzers are pure functions taking artifacts + config, returning dataclasses.
- **`D3`**: Dedup artifacts by content hash (not just path) so shared templates/refs collapse.
- **`D4`**: 4-chars-per-token heuristic for static token estimation.
- **`D5`**: Deterministic Jaccard + bag + name overlap; pluggable MiniMax interface for semantic.
- **`D6`**: DFS for cycle detection (Tarjan's SCC is overkill for small graphs).
- **`D7`**: Strip frontmatter from body before action extraction.
- **`D8`**: Log-scaled reuse (10 uses = 0.6, 100 uses = 1.0) so 1-time-use skills aren't crushed.
- **`D9`**: Output quality = `100 - 50*blocking - 25*warning` so blocking findings dominate.
- **`D10`**: Recommendations: per-artifact first, then layer in merge/split, sorted by priority.
- **`D11`**: Rewrites are *proposals*, not auto-applied. CI blocks on missing metadata but does NOT auto-rewrite.

### 7 lessons learned (this segment, #48-#54)

- **#48**: Discovery must dedup by content hash, not just path. A skill with shared `references/` subdirs causes duplicates.
- **#49**: Body excerpts that include frontmatter pollute responsibility counting. Strip frontmatter before action extraction.
- **#50**: When the metadata parser needs a discovery root to resolve relative paths, pass the root explicitly rather than guessing from CWD.
- **#51**: Recommendations need a fallback decision when no scorecard is available. Default to REWRITE on blocking findings, KEEP otherwise.
- **#52**: Benchmark scoring with empty rules = score 1.0. A fixture with no rules is vacuously passing.
- **#53**: Rewrites should always include the original excerpt (capped at 500 chars) so the human reviewer can see what they're rewriting.
- **#54**: Waivers need an explicit `is_valid()` method to filter out incomplete entries. An entry with no `expiration_date` is invalid by definition.

## SGP Phase 6 — BDD-TDD closes 4 v1.0.0 gaps (2026-06-14)

Triggered by the "Recommend features or improvements for SGP?" question
(2026-06-14T01:30Z). Justin said "yes, ensure you follow the BDD-TDD
methodology" — so I wrote 7 acceptance tests FIRST, watched them fail,

### Method

  (Given/When/Then in docstring, assertion in test function name)
- Red phase: 6/7 fail against v1.0.0 (1/7 is the self-test)
- Green phase: 4/4 fixes implemented, 7/7 acceptance tests pass,
  75 existing tests still pass → **82/82 total**

### Fixes

**Fix #1 (CLI surface is 5/8):** refactored `ci` to delegate to
`_run_full_pipeline()` helper; the 3 stubbed commands
(`benchmark`, `recommend`, `rewrite`) now run end-to-end. Each
writes its expected output file.

**Fix #2 (health score formula):** was `100 - 5*blocking - warnings`
which always gave 0 for any catalog with 20+ blocking findings. New
formula is per-artifact: clean=100, ugly (cosmetic only)=80, broken
(structural blocking)=30, weighted average. **Real catalog: 0 → 69/100.**
This single change reframes the rewrite proposals from "all 126 are
rewrite" to "the 4 with structural issues are broken, the rest are
ugly but working" — a much more honest signal.

**Fix #3 (unknown artifacts):** `unknown`-type artifacts (README,
templates) now get a single `untyped.skipped.{name}` warning instead
of 34 blocking contract findings.

**Fix #4 (finding IDs):** added `artifact_path: str | None` to the
`Finding` model. All findings stamped with the source artifact's
relative path. Downstream consumers can now group findings by
artifact (was impossible before).

### Side-effect: path resolution bug

The `_validate_one` function was resolving `artifact.path` against
`config_path.parent.parent` (2 levels up from the config file).
This was fragile and wrong in general. The existing v1.0.0 test
had 5/5 findings that were false-positive "Path does not exist"
findings; the real catalog had 133 blocking findings where most
were this same bug. Fixed by resolving against the actual
discovery roots, like the other analyzers do. **This is the
single most impactful fix in the phase** — it makes 80+ of the
v1.0.0 catalog findings go away.

### New lessons #58, #59, #60

- **#58**: When refactoring a "do everything" command into a
  shared helper, the sub-phase commands can call the same helper
  with `render_reports=False` and only get the slice they need.
  This is a clean pattern (avoids duplication) but means the
  "command X writes file Y" promise of the sub-phase command
  must be checked at the end of the helper.
- **#59**: For health-score formulas, "100 minus penalty" always
  clamps to 0 for catalogs with many findings. Use a per-artifact
  model (clean/ugly/broken → 100/80/30 weighted) instead. Much
  more meaningful.
- **#60**: SGP's `_validate_one` was the only analyzer that used
  `config_path.parent.parent` for path resolution; the others
  iterated over discovery roots. This kind of inconsistency is
  why the v1.0.0 catalog had so many false positives. When
  multiple modules do similar things, make sure they use the
  same approach.

### Fixes

**Fix #1 (64 false merges → 0):** `score_roi()` had a bug at
`roi_scorer.py:144`. `has_merge_candidate` was computed from
`findings with category == 'overlap'`, but overlap produces
`OverlapPair` objects, not `Finding`s. The check was always False.

with score 30-49 got tagged merge regardless of actual overlap.

now uses real overlap data. **64 → 0 false merges.**

**Fix #2 (ci output 1 line → 6+5 line summary + JSON block):**
The `ci` command now prints a multi-line human summary (artifacts,
findings, blocking, health, top-3 blocking categories, report path)
followed by a sentinel-delimited JSON status block. Both new tests
parse the output and verify structure.

**Fix #3 (runtime_metrics.ingest stub → real JSONL parser):**
Was: `def ingest(): return []`. Now: parses JSONL files,
aggregates per artifact, returns list of `RuntimeTokenMetrics`.
Accepts single path or list. Malformed lines skipped silently.
Both new tests pass.

### Side-effect bugs (uncovered by acceptance testing)

**Bug #1a (artifact_name_from_path):** For paths of the form
`root/<skill-name>/SKILL.md` (2 parts), the function returned
`skills/SKILL` (file stem) instead of `skills/<skill-name>`. Made
overlapping skills look identical. Test 1b caught this.

**Bug #1b (overlap_analyzer._recommendation hardcoded):** Function

### New lessons #63, #64, #65

- **#63**: A conditional like `decision = X if cond_a or cond_b`

  concrete instance.
- **#64**: BDD acceptance tests catch side-effect bugs in the

- **#65**: Phase 6 made the health score meaningful (0 → 69/100)

### New lessons #87, #88, #89, #90, #91

- **#87**: mutmut's `mutants/` chdir is broken for non-targeted source
  files. When you have a 21-module Python project and try to mutate
  one module, mutmut's chdir forces the test to load its copied
  src/ which lacks the OTHER 20 modules → import errors. Workaround:
  write a manual mutation script that (a) reads the source file,
  (b) writes a one-line replacement for the mutation, (c) runs the
  targeted tests via subprocess, (d) restores the original. The
  script lives in the task workspace as a re-runnable artifact
  (mutation-check.py). For 79 new tests across 2 PRs, this script
  killed 23/24 mutants (96%).

- **#88**: BDD-TDD docstrings + assertion-named functions are durable
  across merges. Pattern: function name = the assertion
  (e.g. `test_analyze_runtime_emits_deprecation_warning`), docstring
  = Given/When/Then. 79 tests over 2 PRs (P1 + P2/P3) stayed
  self-documenting through 2 merges with no test rewrites. The cost
  is 4-6 lines of docstring per test; the benefit is that anyone
  reading a test can answer "what does this test?" without reading
  the assertion. Stick with this for all future gap-closure work.

- **#89**: Observational equivalence is a real thing for surviving
  mutants. When two operations/branches are interchangeable for the
  test inputs, the test cannot distinguish them. Real example:
  `discovery.classify_artifact` — swapping AGENT-then-SKILL with
  SKILL-then-AGENT produces identical output when the parent dir
  only matches ONE of the patterns (e.g. `agents/SKILL.md` has only
  AGENT in the parent). The mutation "survived" the test suite, but
  the test is still correct — the swap is just a no-op for the
  inputs I tested. The honest report is "8/9 killed; 1 legitimate
  survivor" rather than chasing the survivor. A future test that
  exercises a path where BOTH patterns match in the parent would
  catch this; that's a real improvement worth scheduling.

- **#90**: A stub with `# pragma: no cover` is a docstring liability.
  The `token_analyzer.analyze_runtime` function was a stub returning
  `[]` with a docstring that promised "Phase 2 will define a log
  format". Phase 2 actually happened in `runtime_metrics.ingest()`.
  The stub's docstring made the relationship to the real impl
  invisible to users. Resolution: deprecate the stub, emit a
  `DeprecationWarning` pointing to the canonical replacement, and
  delegate. The deprecation path is cheaper than re-implementing
  and preserves backward compat. The `# pragma: no cover` is
  removed (since we now exercise the path with the deprecation
  test). General principle: if a stub's docstring lies about
  future plans, the right fix is to make the docstring honest
  (deprecate) rather than to implement the lie.

- **#91**: When splitting finding categories downstream, verify the

### New lessons #92, #93, #94, #95

- **#92**: When the application-test-coverage workflow is run against
  a subpath project (like `aiWorkflows/skill-governance-pipeline/`),
  the ledger must live inside the subpath, not at the input repo
  root. The 3-step rule for determining the project root:
  (1) If `MODULE_LIST` has entries, the project root is the
  narrowest directory containing all source files in any module.
  (2) If no `MODULE_LIST` and the repo has a single subpath
  matching the workflow's expected layout, use that subpath.
  (3) Otherwise, the project root is the repo root. Encode this
  as a `PROJECT_ROOT` input defaulting to rule (3).

- **#93**: LLM-prompt-driven workflows have a quiet failure mode:
  the prompt says "write FILE_X" but does not say WHERE. The LLM
  picks a sensible default (often the repo root), which is wrong
  for subpath projects. Fix: every prompt that emits a ledger
  must include a LOCATION block right after PRIMARY OUTPUT.
  Don't trust the LLM to infer the path from context.

- **#94**: When auditing workflows for the same anti-pattern, do a
  3-pass sweep: (1) grep for `TODO_<name>.md` mentions in prompts,
  (2) check if each mention is followed by a LOCATION block,
  (3) check the recovery doc to see if the resume procedure
  assumes a specific path. If any of the 3 is silent on the path,
  the workflow has the bug. This is faster than re-reading every
  prompt from scratch.

- **#95**: For workflow-level fixes (rules, prompts, recovery docs,
  validation gates), commit them as a single PR with one logical
  change. Don't fragment into "rule change" + "prompt change" +
  "validation change" commits; they're all the same fix. The
  12-file change in commit bc54657 reads as one PR with 3
  intent-blocks: "add the rule", "apply the rule to each workflow",
  "add a gate to enforce the rule". Future maintainers can
  understand the intent from the commit message.

### Push pattern: direct-to-main vs PR (resolved)

After bc54657 went straight to main (matching the pattern of e10eedb
and 9b3e41f in this session), Justin asked: "Changes applied and a
PR created?" — which I read as expecting a PR. I offered to convert
bc54657 to a branch + PR. Justin replied "No."

**Resolution:** Direct-to-main is the correct pattern for aiWorkflows
harness/workflow edits. Justin's "Changes applied and a PR created?"
was a clarification question, not a correction — he wanted to confirm
the change was actually applied (it was: commit + push to main) and
to check the deliverable shape. The follow-up "No" to my conversion
offer confirms: he doesn't need a PR review surface for harness edits.

**Revised lesson #96** — *Push pattern for aiWorkflows:*
- **Source code changes to a project (e.g. SGP):** branch + PR +
  squash-merge (the #45/#46 pattern). Even when Justin is the only
  committer, the PR provides a review surface and a clean merge
  point for session-bounded work.
- **Harness / workflow / memory edits to aiWorkflows itself:**
  direct-to-main, single commit, descriptive message. No PR. The
  file paths (workflows/, memory/) make the scope self-evident and
  the diff is small enough to read in one go.
- **Doc fixes, .gitignore updates, file moves:** direct-to-main.
- **Cross-cutting refactors of harness (12+ files):** consider
  one branch + PR for the session, but ship as direct-to-main if
  the commit message clearly describes the intent and the diff
  is reviewable in one pass.

The differentiator is **review surface need**, not file count.
PR is for changes that benefit from a checkpointed review before
merge; direct-to-main is for changes that are self-evidently
correct or too tactical to warrant a separate review step.
